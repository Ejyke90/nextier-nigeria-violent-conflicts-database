## 1. The RAG Landscape — Research Synthesis

In 2024 alone, over 1,200 RAG-related papers appeared on arXiv. The field has matured from naive "retrieve-and-read" into a modular, production-grade architecture. Here is a synthesis of the most relevant findings for this PoC.

### 1.1 The Three Generations of RAG

| Generation | Description & Relevance to PoC |
|---|---|
| **Naive RAG** | Fixed pipeline: chunk → embed → retrieve top-K → generate. Fast to build, mediocre recall, context loss common. Good baseline. |
| **Advanced RAG** | Pre-retrieval (query enrichment, rewriting, expansion) + post-retrieval (reranking, compression). Adds query enrichment stage — what the LLM Gateway implements. |
| **Modular / Agentic RAG** | Tools-based, iterative, self-correcting retrieval loops. Agent decides when and what to retrieve. Maps to our MCP tool architecture perfectly. |

### 1.2 The Central Insight from Anthropic Research

Anthropic's published "Contextual Retrieval" research (Sept 2024) is the single most important reference for this PoC.

> **FINDING:** Contextual Embeddings alone reduce retrieval failure by 35%. Contextual Embeddings + Contextual BM25 reduce failure by 49%. Adding a reranker reduces failure by 67% (from 5.7% to 1.9%).

The method prepends a 50-100 token chunk-specific context (generated by an LLM reading the whole document) to each chunk before embedding AND before BM25 indexing. For emails, this means: prepend subject, sender, thread, date, and a brief LLM-generated situational summary to each email chunk before indexing.

### 1.3 Hybrid Search — The Architecture in Image 3

The whiteboard "Fusion Retrieval / Hybrid Search" diagram maps directly to the most validated approach in the literature. The research consensus:

- **Semantic search** (dense vector) captures intent and meaning — misses exact keyword matches
- **BM25 / Sparse retrieval** captures exact terminology, project codes, names, technical terms — misses paraphrases
- **Reciprocal Rank Fusion (RRF)** is the gold-standard method for combining ranked lists from both sources
- **Set Union** (not intersection) of top-K from each source maximizes recall before reranking

> **For the email use case:** Project names like "Konek ID", testing cycle numbers, and status keywords (e.g. "E2E", "Preauth", "Cycle 2") are exactly what BM25 excels at. Semantic search catches paraphrases like "status update" matching "execution status". Hybrid is non-negotiable for this domain.

## 2. Query Enrichment — The LLM Gateway Layer

This is the stage the meeting notes explicitly flag: the LLM Gateway enriches the raw user query with contextual keywords before RAG search begins. This maps to a well-studied technique with several implementation variants.

### 2.1 Techniques Identified in Literature

#### 2.1.1 Query Rewriting / Expansion

The simplest and most proven approach: pass the user's raw query to a small/fast LLM and ask it to rewrite or expand the query for better retrieval.

- **HyDE (Hypothetical Document Embeddings):** LLM generates a hypothetical ideal answer, then that answer is embedded for retrieval — powerful for "what would the email saying X look like?" patterns
- **Multi-Query Expansion:** LLM generates 3-5 rephrased variants of the query, each is run through retrieval, results are union-merged — catches more relevant docs with different surface forms
- **Step-Back Prompting:** LLM generates a broader, more general version of the query — good for "What happened with project X?" expanding to capture status reports, meeting notes, and email threads

#### 2.1.2 UniRAG (ACL 2025)

The most recent work from ACL 2025 proposes unified query augmentation that adaptively selects the right strategy per query type: no augmentation, rewriting, expansion, or HyDE — based on the query characteristics. This is the state-of-the-art approach but requires training. For a 1-day PoC, a rule-based or prompted version is more practical.

#### 2.1.3 Keyword Extraction / Metadata Injection

The meeting notes show the LLM Gateway enriching with "contextual keywords (Not using Full-text search with FTS5/BM25)" — but the architecture should evolve to include both. The Gateway can extract:

- Named entities: project names, person names, team names
- Temporal signals: dates, "last week", "Q3", cycles
- Status keywords: "completed", "blocked", "in progress", "testing"
- Action/intent: "status", "update", "review", "approval"

> **RECOMMENDATION:** For the 1-day PoC: implement a simple LLM prompt that takes the user query and outputs a JSON with: (1) `rewritten_query`, (2) `extracted_keywords[]`, (3) `inferred_date_range`, (4) `query_type` [status|search|summary]. Use this to drive different retrieval strategies.

### 2.2 Not Using BM25 in the Gateway — A Potential Gap

The meeting notes indicate the current thinking avoids FTS5/BM25 for query enrichment. This is worth questioning during experiments. The research is clear: BM25 complements semantic search. The enrichment Gateway doesn't need to run BM25 itself — but the enriched query's keywords should be fed to the downstream BM25 index in the retrieval layer.

## 3. Email Ingestion Pipeline — Key Design Questions

Emails are semi-structured documents with a unique combination of metadata richness (sender, subject, date, thread-id, distribution list) and narrative text. The ingestion design has outsized impact on retrieval quality.

### 3.1 Chunking Strategy for Emails

Standard chunking research (recursive character splitting, 300-500 tokens) is designed for long-form documents. Emails are different:

| Email Type | Chunking Approach |
|---|---|
| **Short transactional emails** (<200 tokens) | Store as single chunks — no splitting needed. Metadata-rich, single semantic unit. |
| **Long email threads** | Split by message boundary (each reply is a separate chunk). Preserve thread hierarchy in metadata. |
| **Status report emails** | Split by section headers if structured (e.g., "Summary:", "Details:", "Next Steps:"). These map to specific query intents. |
| **Forwarded chains** | Extract and chunk each layer separately. Tag original vs. forwarded content. |

### 3.2 Metadata to Extract and Index

This is the highest-leverage action for email RAG. Rich metadata enables pre-filtering before vector search, dramatically improving precision:

- `from_email`, `to_emails[]`, `cc_emails[]`, `bcc_emails[]`
- `subject` (original and cleaned/normalized)
- `date`, `thread_id`, `message_id`, `in_reply_to`
- `distribution_list_name` (key for scoping queries)
- `extracted_project_names[]` (via NER or LLM extraction)
- `extracted_status_keywords[]` (via pattern matching)
- `email_type`: [status_report | meeting_invite | action_item | FYI | thread_reply]
- `llm_generated_summary` (50-100 tokens — the contextual retrieval context)

### 3.3 The Contextual Retrieval Layer for Emails

Applying Anthropic's Contextual Retrieval to emails means: before embedding each email/chunk, prepend an LLM-generated context block like:

> *"This email is from Kevin Sivaperumal (Project Lead) sent September 12, 2025 to 30+ QA, development, and business stakeholders. It reports the completion of Konek ID Preauth E2E Testing Cycle 2. [original email text follows]"*

This context block is prepended to the raw email text before both embedding generation AND BM25 indexing. It ensures that retrieval for "What's the status of Konek ID?" matches this email even if the original email body only says "Cycle 2 execution completed."

### 3.4 Ingestion Architecture Considerations

- **Incremental ingestion:** new emails should append to the index without full re-indexing
- **Deduplication:** use `message_id` as primary key to prevent duplicate entries
- **Prompt caching:** when generating contextual summaries for many emails, Anthropic's prompt caching can reduce costs by up to 90%
- **Thread-aware chunking:** store parent thread context with each reply chunk to preserve conversational coherence

## 4. The Four Search Endpoints — Brainstorm & Research

Each endpoint corresponds to a different point on the accuracy/latency/cost tradeoff curve.

### 4.1 Tool 1: `email_query` — Basic Search

**Purpose:** Fast, low-latency lookup using metadata filters and exact keyword matching. No LLM in the retrieval path.

- Implementation: SQL-style filter on indexed metadata (from, subject, date range, project_name) + optional FTS5 keyword match
- Use case: *"Show me all emails from Kevin about Konek ID in September 2025"*
- Stack: SQLite with FTS5 extension — no infrastructure dependencies, WAL mode for concurrent reads, fast
- Latency target: **<50ms** — this should feel like a database query

> **PoC TECH NOTE:** SQLite + FTS5 + Python FastAPI has been validated in production for read-heavy workloads. 384-dim embeddings (MiniLM) cut CPU usage 4x vs 1536-dim with comparable results for domain-specific search.

### 4.2 Tool 2: `search` — Semantic Search

**Purpose:** Embedding-based similarity search. Query intent and paraphrases captured even without keyword overlap.

- Embed user query → cosine similarity against email chunk embeddings → top-K results
- Embedding model options: `text-embedding-3-small` (OpenAI), `voyage-3-lite` (Anthropic/Voyage), `nomic-embed-text` (open source, 768-dim, strong performance)
- Vector store for PoC: ChromaDB (in-memory or persistent) or sqlite-vec (zero infrastructure). Production: Qdrant, Pinecone, or pgvector.
- `top_k` parameter: expose this in the MCP tool schema. Research suggests top-20 is the sweet spot before reranking.

### 4.3 Tool 3: `full_rag` — Hybrid + Reranker + LLM Augmented

**Purpose:** Highest-quality endpoint. Maps directly to the "Combined" slide (Image 4) and the hybrid search diagram (Image 3).

**Runtime flow:**

1. **Query enrichment:** LLM Gateway expands/rewrites query, extracts keywords
2. **Parallel retrieval:** Semantic search (vector) + BM25/FTS5 (keyword), both using enriched query
3. **Rank Fusion:** Reciprocal Rank Fusion (RRF) combines results. Formula: `score = 1/(k + rank)`, k=60 is standard. Union of results from both retrievers.
4. **Reranking:** Take top-N (25-50) fused results → pass to cross-encoder reranker → return top-k (3-5) for LLM context. Options: Cohere Rerank v3, `mixedbread-ai/Mxbai-Rerank-Large-V2` (open source), Voyage Rerank
5. **LLM Generation:** Top-k chunks + enriched query → LLM → structured response

> **KEY INSIGHT:** The research consensus: over-retrieve broadly (top-25 to top-150 depending on corpus size), then aggressively filter down with a reranker. This 2-stage approach decouples recall (retriever's job) from precision (reranker's job).

### 4.4 Tool 4: `report_generation` — Executive Report

**Purpose:** Given a query (or retrieved results), produce a structured executive-level communication in a fixed template.

**Executive report template structure (fixed):**

1. **Executive Summary** (2-3 sentences): what the query found, key status
2. **Key Findings** (bullet list): most relevant facts from retrieved emails
3. **Source Attribution**: which emails, from whom, dated when
4. **Timeline / Status**: chronological progression if multiple emails
5. **Action Items / Open Questions** (if any surface from the emails)
6. **Confidence Note**: how many relevant documents found, retrieval quality signal

The LLM prompt for report generation should be templated and fixed — consistent format every time is more valuable for executive consumption than creative variation.

## 5. MCP Server Architecture — Research & Design

The Model Context Protocol (MCP) is a standardized protocol enabling AI assistants (Claude, Cursor, Copilot, etc.) to connect to external tools without custom per-integration code. There are now 4,400+ MCP servers on mcp.so (April 2025).

### 5.1 MCP vs REST API — Both Are Required

| Interface | Purpose & Notes |
|---|---|
| **MCP Interface** | For IDE integration (Cursor, VS Code Copilot, Claude Code), AI agent orchestration, and any MCP-compliant client. Tool discovery via standard handshake. |
| **REST API Interface** | For programmatic access, web frontends, non-MCP AI assistants, testing, and any system that speaks HTTP. FastAPI is the right choice. |
| **Relationship** | MCP server wraps the same core RAG service that the REST API exposes. Same business logic, two protocol interfaces. |

### 5.2 MCP Transport: stdio vs HTTP/SSE

- **stdio transport:** for local IDE integrations (Cursor, Claude Desktop). Simpler setup, lower latency, no port management.
- **HTTP/SSE transport:** for remote deployment, multi-client scenarios, Claude in browser, API-accessible scenarios.
- **PoC recommendation:** implement stdio first (fastest to validate in Cursor/Claude Code), expose HTTP transport flag via env var for remote access.

### 5.3 MCP Tool Schema Design — Research Note

A recent paper "RAG-MCP" (May 2025) found that giving an LLM too many MCP tool descriptions causes "prompt bloat" — accuracy drops from 43% to 13% when all tools are visible. The recommendation: design each tool with crystal-clear, discriminating descriptions.

| Tool | When to Use (appears in MCP tool description) |
|---|---|
| `email_query` | Use when: known sender, subject, or date range. Fast metadata/keyword lookup. Returns raw email records. |
| `search` | Use when: semantic question about email content without specific sender/date. Returns semantically similar email chunks. |
| `full_rag` | Use when: complex question requiring highest accuracy, synthesis across emails, or when simpler search returns poor results. Slower but most accurate. |
| `report_generation` | Use when: user explicitly wants an executive summary, status report, or structured briefing. |

### 5.4 Implementation Stack for PoC

| Component | Technology Choice & Rationale |
|---|---|
| Language | Python 3.11+ |
| API Framework | FastAPI (async, Pydantic v2, auto OpenAPI docs) |

## 6. Production Best Practices to Bake In From Day 1

Even for a PoC, the following patterns are low-effort to implement and prevent painful refactors later.

### 6.1 Retrieval Quality

- **Prompt caching:** for contextual retrieval generation, cache the "whole document" in the prompt prefix. Up to 90% cost reduction on repetitive LLM calls — critical when generating context for hundreds of emails.
- **Metadata filtering before vector search:** apply sender/date/project filters at the database level before running embeddings. Reduces search space and improves precision at zero extra LLM cost.
- **Chunk overlap:** use 10-20% overlap between chunks to prevent context loss at boundaries. Standard: chunk_size=512, overlap=50-100 tokens.
- **Parent-child chunking:** store small chunks for retrieval, return parent chunk to LLM for richer context.

### 6.2 Observability & Evaluation

- **Trace every retrieval:** log query, enriched_query, retrieved_chunks[], reranker_scores[], final_chunks[], latency_ms, token_count per request. This becomes your eval dataset.
- **RAGAS metrics:** evaluate using RAGAS framework: faithfulness, answer relevancy, context precision, context recall.
- **A/B logging:** log both basic search and full_rag results per query during PoC. Compare retrieval quality without a user ever seeing the comparison.

### 6.3 Architecture Separation

- **Ingestion service:** completely separate from the query service. Can run as a background job or triggered pipeline. Critical for incremental email ingestion without downtime.
- **Dependency injection:** FastAPI's DI system makes vector store, LLM client, and reranker injectable — replaceable without touching endpoint logic. Essential for swapping ChromaDB for Qdrant later.
- **Schema-first API design:** define Pydantic models for all request/response shapes before writing business logic.

### 6.4 Context Management

- **Token budget awareness:** count tokens before sending to LLM. At >50% context window fill, hallucination risk increases significantly. Implement a context compressor for large result sets.
- **Adaptive top-k:** simple queries retrieve 5-10 chunks; complex synthesis queries retrieve 20-25 before reranking. Make this configurable per tool call.
- **MapReduce for large contexts:** if retrieved email set is large, LLM processes each chunk to extract relevant facts, then synthesizes facts into final report. Prevents context overflow.

## 7. Experiments to Run in the 1-Day PoC Sprint

The goal is validation, not perfection.

### Experiment 1: Ingestion Quality
- Input: 10-20 sample emails (short transactional, long status reports, thread replies)
- Run ingestion with and without LLM-generated contextual summary prepended
- Inspect stored chunks and embeddings — do they make semantic sense?
- Measure: ingestion time per email, cost per email for contextual summary generation

### Experiment 2: Retrieval Ladder
Run the same 5 test queries through all three search modes, record top-3 results each:
1. Basic keyword (FTS5/BM25)
2. Semantic only
3. Hybrid (BM25 + semantic via RRF)
4. Hybrid + reranker

Evaluate manually: which mode returns the most relevant emails for each query?

### Experiment 3: Query Enrichment Value
- Run query *"What's the status of Konek ID?"* (raw) through retrieval
- Run the LLM-enriched version through same retrieval
- Compare result sets — does enrichment surface emails that raw query misses?
- Measure: latency overhead of enrichment step (~200-500ms for a small LLM call)

### Experiment 4: MCP Tool Integration
- Stand up MCP server with 4 tools (stdio transport)
- Connect to Cursor or Claude Code
- Issue test queries via the IDE and observe tool selection and results
- Key question: does the LLM correctly discriminate between the four tools based on descriptions?

### Experiment 5: Report Generation Quality
- Feed the same retrieved context to the report template prompt
- Evaluate: is the executive summary accurate, attribution correct, format consistent?
- Iterate on the prompt template — this is where the most user-visible quality lives

## 8. Open Questions & Risk Areas

### 8.1 Data Questions
- **Email access:** IMAP ingestion, exported PST/MBOX, or manual upload? The ingestion connector design depends heavily on this.
- **Volume:** 100 emails vs 100,000 emails changes the vector store and BM25 index technology choices significantly.
- **Permissions:** personalized grounding implies different users see different email subsets. Does the RAG service need to enforce access controls at query time?
- **Email format diversity:** HTML emails, forwarded content with signatures, quoted text — all create noise in chunking. How much preprocessing is needed?

### 8.2 LLM Gateway Design
- Which model for query enrichment? Fast/cheap (Haiku) vs slow/better (Sonnet)? The latency tradeoff matters for MCP tool response times.
- Is the LLM Gateway stateful (conversation history) or stateless? For project status queries, conversation context could improve enrichment.
- Cost per query enrichment call at scale?

### 8.3 Reranker Availability
- Cohere API requires an API key and has costs — viable for PoC? Alternative: local cross-encoder (no API dependency) is heavier but free.
- Reranker latency: adds ~200-500ms to each `full_rag` call. Acceptable for report generation but potentially too slow for real-time chat.

### 8.4 MCP Ecosystem Compatibility
- Claude Code, Cursor, and VS Code Copilot all support MCP but with slightly different configuration file formats and discovery mechanisms. Need to validate in at least one IDE.
- Authentication: the MCP server will need to handle API key management for downstream LLM/reranker calls without exposing secrets to the client IDE.
